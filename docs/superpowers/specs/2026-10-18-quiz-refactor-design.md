## 3. 已验证的问题与改进点

### 3.1 评分可复现性与机会分布：最高优先级

现有评分是把每个已提交选项的分数加到相应类型，最后直接比较原始总分。最高分并列时用 `Math.random()` 选一个类型。[评分代码](https://github.com/WudiWZH801/Gay-test/blob/04c27afcf9e6facca87c1b55e224f9e9b4b304d9/index.html#L492-L521)

已穷举全部 `4^10 = 1,048,576` 种答案序列，结果如下：

- 175,117 种序列出现最高分并列，占 **16.70%**；最多有 **7 个类型**同时并列最高分。
- 示例答案 `AAAAAABAAB` 中，傲娇女王型和高冷男神型均为 13 分。浏览器中保持得分不变，仅控制随机数，就能分别显示这两个结果。
- 8 个类型都存在独立获胜的答案组合，没有发现完全无法出现的类型。
- 类型得分机会明显不同；直接比较原始总分会把这种差异带到输出结果中。

| 当前类型 | 所有选项提供的分数总和 | 单次测试可达最高分 | 独立获胜组合数 | 模型中的预期结果占比 |
| --- | ---: | ---: | ---: | ---: |
| 傲娇女王型 | 30 | 27 | 133,953 | 14.76% |
| 阳光奶狗型 | 42 | 27 | 283,329 | 31.28% |
| 高冷男神型 | 30 | 23 | 100,915 | 11.68% |
| 文艺青年型 | 26 | 22 | 57,054 | 6.83% |
| 毒舌妖精型 | 26 | 20 | 40,390 | 5.05% |
| 居家暖男型 | 35 | 26 | 133,795 | 15.42% |
| 霸道总裁型 | 20 | 18 | 18,097 | 2.32% |
| 沙雕欢乐型 | 34 | 25 | 105,926 | 12.65% |

统计口径：所有答案序列等权，相当于每题的 4 个选项独立、等概率被选中；同分时按现有均匀随机规则平均分摊获胜机会。这是代码分析模型，**不是真实用户数据，也不是心理测量有效性证据**。最常见与最少见类型的模型占比相差约 13.5 倍，值得在内容与配分设计中修正。

### 3.2 状态与评分、DOM 相互耦合

当前只保存累计分数和正在选择的选项，没有完整答案记录。推进题目时直接修改得分，渲染函数又会清空选择状态。由此带来的限制是：无法返回修改、刷新不能恢复、难以重算或解释结果，测试也必须依赖页面环境。[状态与渲染代码](https://github.com/WudiWZH801/Gay-test/blob/04c27afcf9e6facca87c1b55e224f9e9b4b304d9/index.html#L429-L507)

建议以答案记录作为唯一计分依据；页面只渲染状态，评分函数根据答案重新计算。这样能支持回退修改，并避免未来加入回退功能后产生重复加分或漏减分。

### 3.3 键盘操作与焦点管理不完整

选项是带 `role="radio"` 的 div，但没有 radiogroup、题目关联或单选组的方向键行为。每个选项都是 Tab 停靠点。浏览器实测：按方向键不会切换选项；空格可以选择；选择后按 Tab 会进入下一个选项。[选项代码](https://github.com/WudiWZH801/Gay-test/blob/04c27afcf9e6facca87c1b55e224f9e9b4b304d9/index.html#L462-L470)

开始测试和切换题目后，实测焦点会落到 body，页面没有主动把焦点交给新题目或结果标题。建议使用原生 `fieldset`、`legend`、`input type="radio"` 和 `label`，并统一处理切屏焦点及状态提示。单选组预期行为参考 [W3C Radio Group Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/radio/)。

### 3.4 答题连续性与反馈不足

这些属于功能补足或交互优化，不能全部视为现有实现的错误：

- 缺少“上一题”和修改答案入口。
- 刷新会回到欢迎页，已答内容全部丢失，已在浏览器复现。
- 进度条按题目索引计算：第 10 题时为 90%，完成后答题页直接隐藏，未提供明确的完成进度语义。
- 没有针对减少动态效果偏好的样式；存在切题动画、强制布局读取和结果页平滑滚动。
- 辅助文字较浅、结果正文较长，适合统一文字层级、颜色和内容密度；本次所测移动宽度没有发现横向溢出。

### 3.5 题库与类型边界需要重新设计

现有“女王/总裁”的控场特征、“奶狗/暖男”的陪伴特征、“女王/毒舌”的表达方式存在交叉；交叉本身可以有趣，但当前缺少明确的类型边界和配分规范。

部分题目把日常偏好与明显的道德评价混放，例如“最受不了的行为”；部分场景的选项都不贴近日常，例如约会迟到两小时的原因。结果还存在没有被题目充分支撑的具体断言，如厨艺、固定身体照顾情景，以及缺乏规则依据的适配关系。[题库](https://github.com/WudiWZH801/Gay-test/blob/04c27afcf9e6facca87c1b55e224f9e9b4b304d9/index.html#L334-L425)、[结果文案](https://github.com/WudiWZH801/Gay-test/blob/04c27afcf9e6facca87c1b55e224f9e9b4b304d9/index.html#L251-L332)

建议先定义各类型的独特表现，再写场景和选项；让选项都是可以理解的偏好，结果用娱乐角色画像解释这些偏好。

### 3.6 工程保障与内容维护不足

- 样式、类型、题库、状态、评分、DOM 操作全部在同一文件；修改一处容易影响其他职责。
- 题目与选项没有稳定 ID，适配类型用展示字符串硬编码；改名和调整顺序缺少校验。
- 缺少数据校验、核心规则测试、开发说明和自动检查。
- 内联 `onclick` 与全局函数耦合；大量 `innerHTML` 拼接混合了结构与文案。当前数据全部来自源码常量，**没有确认可利用的用户输入注入路径**；建议作为结构整理处理，不将其包装成已发生的安全漏洞。
- 页面缺少 description、分享预览元信息和 JavaScript 不可用时的提示，可在基础页面整理时补齐。

## 4. 技术路线比较与推荐

| 路线 | 收益 | 代价 | 适用判断 |
| --- | --- | --- | --- |
| 原生 JavaScript 模块拆分 | 改动和工具链最少，容易继续静态发布 | 数据与状态结构依赖约定或 JSDoc，约束较弱 | 适合只做小规模整理 |
| **TypeScript + Vite + 原生 DOM（推荐）** | 题库、类型和状态有编译期约束，评分可独立测试；生产仍为静态资源 | 新增开发依赖、构建命令，需要适配 Pages 发布 | 适合本次代码、题库及评分一起调整 |
| React/Vue + TypeScript | 复杂页面、组件共享和后续功能扩展更便利 | 增加运行时依赖、迁移面和维护概念 | 当前三屏测试应用的收益有限 |

推荐使用 TypeScript、Vite 与原生 DOM。选择依据是当前规模与维护需求，而非框架偏好。Vite 提供原生 TypeScript 模板和静态构建能力，见 [官方入门文档](https://vite.dev/guide/)。不以重构后一定更快作为验收承诺；当前页面本身已经很小，主要收益是规则可靠和维护清晰。

建议职责结构如下。每个文件对应具体职责，避免仅为拆分而增加层级：

  ui/
    welcome.ts               欢迎页

    result.ts                结果及规则说明
  storage.ts                 当前标签页的进度保存与恢复校验
tests/
  scoring.test.ts             核心评分、同分、输入边界与数据约束
  quiz-state.test.ts          回退修改、完成与重置

## 5. 推荐的内容与评分设计

### 5.1 类型：保留 8 类规模，重新区分角色

以下是建议采用的新名称和各自的中心特征，保留原有类型的辨识线索。它们是娱乐角色，不构成心理学分类。

| 建议名称 | 原类型 | 重点表现 |
| --- | --- | --- |
| 闪耀主角型 | 傲娇女王型 | 展现自我、仪式感、希望被看见 |
| 阳光直球型 | 阳光奶狗型 | 热情靠近、直接表达、情感回应 |
| 慢热观察型 | 高冷男神型 | 先观察、重边界、熟悉后投入 |
| 浪漫共鸣型 | 文艺青年型 | 想象、氛围、情绪共鸣 |
| 机智吐槽型 | 毒舌妖精型 | 语言机锋、幽默、用调侃建立连接 |
| 安心陪伴型 | 居家暖男型 | 稳定、照顾细节、日常行动 |
| 果断领航型 | 霸道总裁型 | 决策、担当、组织推进 |
| 随性搞怪型 | 沙雕欢乐型 | 即兴、玩心、制造意外乐趣 |

重写每类的短标签、性格画像、相处方式、优势和容易踩到的坑。适配部分改为有解释的“互动搭配彩蛋”，通过类型 ID 引用，避免改名后残留旧名称。

### 5.2 题库：保持 10 题 × 4 选项

建议题目覆盖：聚会选择、安慰喜欢的人、安排双人周末、陪朋友度过低落、约会遇到意外、表达好感、处理分歧、安排独处空间、一起完成任务、制造日常小惊喜。

每个选项都应描述具体行动，避免用“善良/自私”等显然有优劣的选项替代偏好差异。类型特征跨题重复观察；四个选项长度与吸引力尽量接近。调整的是题库与配分内容，保留轻松、有梗、可在几分钟内完成的节奏。

### 5.3 评分：固定预算、明确并列、答案可重算

建议规则：

1. 每个选项给一个主要类型 **2 分**、一个不同的次要类型 **1 分**，每个选项总分均为 3。
2. 每题覆盖 8 个类型，每个类型只出现一次：4 个主要位置、4 个次要位置。
3. 10 题中，每个类型各占 5 个主要位置、5 个次要位置。因此各类型可达最高分均为 15 分，在选项等概率模型下的平均得分均为 3.75 分。
4. 得分只从已保存的答案记录计算，修改前题后重新计算，不对历史累计值做加减修补。
5. 唯一最高分时显示单一类型；最高分并列时显示“复合型”及全部并列类型标签，并提供对应解读。显示顺序固定，仅用于排版，**不用于暗中选出赢家**。取消随机判定。
6. 得分说明为游戏偏好得分。若展示百分比，明确分母与含义，避免称为性取向概率、准确率或专业测量结果。

相同的得分预算并不自动保证相同的结果分布，因此仍需穷举验证类型之间的共同得分关系。建议把以下约束作为题库验收条件：每类都能独立成为最高分；等概率模型、并列平均分摊口径下，最高与最低类型出现率之比不超过 2。该阈值是排查配分偏置的工程约束，不要求真实用户的结果平均分布。

## 6. 推荐的用户体验范围

- 增加上一题；返回时保留选择，改选后重新计分。
- 使用当前标签页的 `sessionStorage` 自动保存进度；刷新后提供继续或重新开始。保存题库版本和数据版本，校验失败时清理旧记录并给出简短提示；存储不可用时仍可正常答题。
- 题号与完成进度分别表达，选择、切题和完成反馈保持一致。
- 采用原生单选控件、完整可见焦点、切屏焦点管理、结果标题和进度状态提示。
- 保持紫色渐变与卡片风格，统一排版、按钮、文字对比度、间距和移动端触控体验；支持减少动态效果偏好。
- 保留娱乐用途说明，结果页也提供简短的规则入口。答案继续只在本地处理。

## 7. 实施顺序与验收标准

审批通过后按以下顺序实施，每一步保持应用可运行：

1. **建立基线与工程入口**：保留原版基线，创建独立重构分支，建立 TypeScript/Vite 开发与静态构建入口。
2. **拆出数据、状态与评分**：引入稳定 ID 和版本，完成纯函数计分、状态转换和核心规则验证。
3. **落地题库与类型改版**：按本报告的角色边界、题目覆盖和固定配分预算完成新内容，运行全组合统计并调整异常偏置。
4. **重构页面交互**：连接三屏界面，补齐回退修改、恢复进度、焦点管理、键盘操作和视觉细节。
5. **完成工程交付**：增加核心测试、自动检查、README 与 Pages 构建配置；汇总前后行为变化和验证结果，以 PR 提供审阅。

| 范围 | 验收要求 |
| --- | --- |
| 评分稳定 | 同一题库版本、相同答案，多次运行得到相同得分及相同结果集合 |
| 类型可达 | 穷举全部 1,048,576 种组合，每个类型均存在独立获胜组合 |
| 配分约束 | 每选项 2+1 分；每题每类出现一次；每类 5 次主要、5 次次要；分布满足上述偏置约束 |
| 并列结果 | 两类或多类并列均有明确、稳定的呈现，没有随机结果或静默优先级 |
| 状态可靠 | 未答不能推进；返回改选有效；重复完成操作不越界；重测彻底重置；刷新可继续；错误或旧版存储可恢复 |
| 数据完整 | ID 唯一，类型引用存在，分值合法，必填结果字段齐全，显示数量由数据生成 |
| 关键流程 | 欢迎→作答→结果→重测，以及返回改选、刷新恢复和复合型结果的浏览器检查通过 |
| 可访问性 | 键盘可完成全流程，单选组有题目名称与原生行为，切屏有合理焦点，减少动态效果生效 |
| 移动布局 | 至少检查 320、390、768、1280 像素宽度的主要页面及长内容，无横向溢出 |
| 工程 | 类型检查、核心单元测试、关键端到端测试和生产构建通过；依赖版本锁定 |
| Pages | `/Gay-test/` 子路径的静态资源正确，构建产物可访问；发布方式在实施时核对仓库设置 |

测试集中验证计分、数据和真实用户流程，不为纯样式或简单实现细节增加重复测试。

Vite 引入构建步骤后，Pages 必须发布构建产物；项目子路径也需要正确的 base。相关要求见 [Vite 的 GitHub Pages 部署说明](https://vite.dev/guide/static-deploy.html#github-pages)。当前仓库使用动态 Pages 发布流程，实施时需要核对并适配，不能只拆源码而遗漏上线方式。
